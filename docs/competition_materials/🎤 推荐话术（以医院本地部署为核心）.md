既然最终场景是**部署到医院本地**，那整个叙事逻辑就应该反过来——**本地部署是目标，云端 API 是过渡手段**。

# 🎤 推荐话术（以医院本地部署为核心）

## 演示时这样说

> "本系统的目标部署环境是**医院内网**，所有患者数据不出院、不上云，满足医疗数据合规要求。
>
> 我们的架构从一开始就为本地化部署做了设计：
>
> - **医学影像 AI 模块已完全实现本地部署**：脑 CT 分类（MobileNetV2）、SHAP 可解释性分析、脑卒中分割模型均在本地 GPU 上运行，**零外部依赖**
> - **数据存储全部本地化**：MySQL、Elasticsearch、MinIO 通过 Docker Compose 一键部署在医院服务器上
> - **大语言模型层面**：我们采用了**渐进式部署策略**——当前开发阶段通过 API 调用云端模型（智谱 GLM-4）来快速验证业务流程和 Agent 编排逻辑；正式交付医院时，将替换为本地部署的开源大模型
>
> 这种策略的好处是：**业务代码和模型部署完全解耦**。我们所有 LLM 调用都基于 OpenAI 兼容接口，只需要把配置文件中的 `base_url` 从云端地址切换到本地地址（如 `http://localhost:11434`），无需修改任何业务逻辑代码。"

# 🛡️ 评委追问应对

### Q: "大模型为什么还没部署到本地？"

> "大模型本地部署涉及三个工程问题，我们正在逐一解决：
>
> 1. **模型选型**：医疗场景对中文专业术语的生成质量要求很高，我们在评估 GLM-4-9B、Qwen2.5-7B-Instruct 等开源模型的医学问答表现
> 2. **量化与适配**：医院服务器通常配备 A4000/T4 级别 GPU（16GB 显存），需要做 INT4/INT8 量化，同时保证诊断报告的术语准确性
> 3. **开发效率**：比赛阶段我们的核心工作是验证**多智能体协作架构**和**RAG+影像分析流水线**的可行性，用 API 调用能让团队并行开发。模型本地化是部署阶段的工程任务，不影响架构设计
>
> 换句话说，我们现在解决的是**'做什么'和'怎么协作'**的问题，本地部署解决的是**'在哪里跑'**的问题。架构上已经完全就绪。"

### Q: "医院内网不能联网，你们的 RAG 联网搜索怎么办？"

> "在医院内网环境下，联网搜索 Agent 会自动降级：
>
> - RAG Agent 检索的是**院内知识库**（部署在本地 Qdrant/Elasticsearch），不需要外网
> - 联网搜索 Agent 在内网中会触发异常，系统通过 `enable_offline_fallback` 配置自动降级为离线响应
> - 医院可以定期在有网络的管理端更新知识库内容，再同步到内网服务器
>
> 所以本地部署后，系统的核心功能——**影像分析、病例检索、RAG 问答、诊断报告生成**——全部可以在纯内网环境下正常运行。"

### Q: "数据安全怎么保障？"

> "这正是我们选择本地部署的原因：
>
> - **数据不出院**：所有 CT 影像、诊断报告、患者信息都存储在医院本地的 MySQL 和 MinIO 中
> - **模型不上云**：影像 AI 模型在本地推理，影像数据不会发送到任何第三方
> - **认证体系**：医生通过账号登录，密码 bcrypt 加密，Session 管理支持替换为 Redis
> - **符合等保要求**：整体架构满足医疗信息系统安全等级保护的基本要求"
