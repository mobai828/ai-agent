   # 🏆 计算机设计大赛省级决赛答辩：AI-Agent 功能板块（问答/RAG/搜索/路由）模拟问答题库

   ## 模块一：多智能体路由与调度机制（Agent Decision）

   ### Q1：关于多智能体的意图识别与动态路由
   **【评委提问】**
   “同学你好，你们系统里有普通对话、RAG 检索、联网搜索还有医学影像等多个 Agent。请问当医生输入一句话时，系统是如何精准判断该调用哪个 Agent 的？如果用户的意图很模糊，系统会怎么处理？”

   **【考察意图】**
   考察多智能体系统的核心编排能力、LangGraph 的使用以及路由逻辑的鲁棒性。

   **【答辩话术】**
   > “各位评委老师好。在智能体的路由调度上，我们基于 **LangGraph** 构建了一个基于状态图（StateGraph）的中央路由中枢。
   > 1. **大模型意图识别**：我们没有使用简单的关键词匹配，而是构建了一个专门的 `decision_chain`。它会综合分析用户的当前输入、是否上传了图片、以及最近 6 轮的上下文历史，通过大模型（如 GPT-4o）输出带有置信度（Confidence）的 JSON 路由决策。
   > 2. **动态降级与兜底**：如果用户意图模糊，导致路由大模型给出的置信度低于我们设定的阈值（`CONFIDENCE_THRESHOLD = 0.85`），或者用户只是在做日常寒暄，系统会默认将其安全地路由到 `CONVERSATION_AGENT`（普通对话智能体），由它通过多轮对话引导用户补充信息，绝不会强行调用医疗诊断模块。”

   ## 模块二：高级 RAG（检索增强生成）技术细节

   ### Q2：关于 RAG 系统的防幻觉与“拒答”机制
   **【评委提问】**
   “医疗领域的问答最怕大模型‘一本正经地胡说八道’（幻觉）。你们在答辩稿中提到使用 RAG 技术锚定临床指南。但在实际代码中，如果本地知识库里根本没有医生问的罕见病知识，你们的 RAG 系统会怎么反应？会强行编造答案吗？”

   **【考察意图】**
   考察对医疗 AI 安全性的理解，以及代码中 `confidence_based_routing` 和 `insufficient_info` 标志位的实现逻辑。

   **【答辩话术】**
   > “我们在设计 RAG 系统时，将‘防幻觉’放在了第一位，并实现了一套**‘置信度评估与动态流转机制’**。
   > 1. **严格的拒答逻辑**：在 RAG 生成阶段，大模型会评估检索到的上下文是否足以回答问题。如果信息不足，模型会触发 `insufficient_info` 标志位，或者输出‘信息不足无法回答’。
   > 2. **无缝流转到联网搜索**：在我们的 LangGraph 状态机中，专门设计了 `confidence_based_routing` 边（Edge）。一旦检测到 RAG 的检索置信度过低，或者触发了信息不足标志，系统**绝对不会强行编造答案**，而是自动将任务重新路由给 `WEB_SEARCH_PROCESSOR_AGENT`（联网搜索智能体），去广域网抓取最新的医学文献来补充回答。这形成了完美的知识兜底闭环。”

   ### Q3：关于 RAG 检索的精度优化（Advanced RAG）
   **【评委提问】**
   “传统的 RAG 往往只是简单地把文档切块然后做向量相似度匹配，这在复杂的医学长文本中效果并不好。你们的 RAG 模块在检索精度上做了哪些深度的优化？”

   **【考察意图】**
   考察对高级 RAG（Advanced RAG）工程实践的掌握（对应代码中的 `QueryExpander` 和 `Reranker`）。

   **【答辩话术】**
   > “为了适应复杂的医疗文本，我们没有采用最基础的 RAG，而是实现了一套**高级 RAG（Advanced RAG）流水线**：
   > 1. **查询扩展（Query Expansion）**：在检索前，我们会先通过 `QueryExpander` 对医生的原始提问进行扩展和医学同义词重写，解决用户提问与文档表述不一致的问题（提高召回率）。
   > 2. **重排序机制（Reranking）**：在向量数据库（Qdrant）初步召回多个文档块后，我们会引入专门的 `Reranker` 模型对这些文档块进行二次交叉打分和重排序。
   > 3. 这种‘先扩展后重排’的漏斗式设计，确保了最终喂给大模型的上下文是最核心、最相关的临床指南段落，大幅提升了回答的专业度和准确性。”

   ## 模块三：联网搜索与多轮对话

   ### Q4：关于联网搜索（Web Search）的数据清洗
   **【评委提问】**
   “你们系统里有一个联网搜索智能体。互联网上的医疗信息鱼龙混杂，甚至有很多虚假广告。你们是如何保证搜索到的信息是可靠的，并且能被有效利用的？”

   **【考察意图】**
   考察 Web Search Agent 的处理逻辑（`WebSearchProcessorAgent`）。

   **【答辩话术】**
   > “我们非常清楚互联网医疗数据的噪音问题。因此，我们的联网搜索不是简单地把搜索引擎的结果直接扔给用户，而是设计了一个 `WebSearchProcessorAgent`（网页搜索处理器）。
   > 1. **权威信源过滤**：我们在底层搜索接口（如 PubMed 搜索）优先定向抓取权威医学期刊、官方卫生机构的数据。
   > 2. **大模型二次清洗**：抓取到的网页内容会先经过处理器的‘提纯’。大模型会结合医生的多轮对话历史（`recent_context`），剔除无关广告和冗余信息，提取出核心的医学证据，最后再整合成结构化、专业化的回答输出给医生。”

   ### Q5：关于多轮对话的上下文管理
   **【评委提问】**
   “在实际问诊中，医生可能会连续追问。你们的普通问答智能体（Conversation Agent）是如何管理多轮对话历史的？如果对话历史太长，会导致大模型超出上下文限制（Token Limit）吗？”

   **【考察意图】**
   考察工程实现中的内存管理（Memory Management）和 Token 控制。

   **【答辩话术】**
   > “在多轮对话管理上，我们依托 LangGraph 的 `MessagesState` 实现了高效的上下文追踪：
   > 1. **动态上下文截断**：为了防止 Token 溢出和无关历史干扰，我们并没有把所有历史记录都喂给模型。在代码中，我们通过 `config.max_conversation_history` 动态截取最近的 N 轮核心对话（例如最近 6 条消息）。
   > 2. **跨 Agent 的记忆共享**：更重要的是，这个上下文是**全局共享**的。比如医生先用 RAG 查了脑卒中的指南，接着追问‘那最新的相关药物是什么？’，此时任务虽然流转到了联网搜索 Agent，但它依然能读取到之前的 RAG 对话历史，从而实现跨智能体的无缝连贯对话。”
